## Process: MOI Builders webinar session (the live developer webinar series)

### Purpose

A recurring live developer webinar in which Adithya demonstrates one MOI capability end to end on Voyage devnet, then sets a challenge so attendees repeat it. Series arc seen in Drive: II Native Assets (2026-06-12), III Agents on MOI / Agent Registry (2026-06-18), IV Swaps (form created 2026-07-03), VII Agentic Payments (form created 2026-08-07, deck exported 2026-08-06). The 18 Jun transcript says "session three of the MOI builder series", with session one on deploying a first logic and session two on minting native assets. Session numbers I/V/VI have no Drive items (see Open questions).

### Trigger or cadence

- Weekly in June (II on Fri 12 Jun, III on Thu 18 Jun; III's transcript says "last week we minted native assets"), irregular after: IV form in early July, VII in early August.
- The 6 Aug standup records the marketing team keeping Thursday free for "Adi" sessions (weekly cadence decision: Wednesday AMA, Thursday AI/developer session, Friday game night).
- Start time 18:22 to 18:23 IST on the two sessions with Gemini notes (2026-06-12 and 2026-06-18).
- Observed length: transcription ended at 00:51:51 for session III.

### Who does it

Adithya presents. A colleague watches chat ("Bertan's going to be helping me out here... drop questions in the chat", III transcript). The meeting is held from the shared org account `info@moi.technology` (the Gemini notes list "MOI Technology" and Adithya as invitees; recording and notes are owned by that account and shared into Adithya's Drive). Video editing is done by an external editor (Process 3).

### Inputs needed before starting

- A working demo against Voyage devnet and a public repo ("the repo link's in the description. Everything I run today is in there", S7 deck slide 1).
- A funded devnet wallet (one covers the whole demo per S7 slide 7; funded from the Voyage faucet at voyage.moi.technology). The recovery phrase is held in the demo repo's environment file (never record its value).
- A deck with the spoken script in the notes (see Steps).
- A bounty or challenge for attendees (III: 500k and 1M token challenges; amounts as Gemini heard them, verify before reuse).

### Steps in order

1. Pick the topic as the next step of the arc. III opens with callbacks to the two previous sessions; S7 closes with a teaser table "three questions, three sessions" (07 Who am I paying? done; 08 What may I spend? next; 09 What if you don't deliver? after).
2. Build the demo repo with setup scripts. S7 slide 7 lists the attendee run-book: `npm install`, `cp .env.example .env`, paste a funded wallet's recovery phrase, `npm run setup:asset` (mint the settlement asset), `npm run setup:registry` (put both agents on chain), `npm run ui` (agent console on `http://localhost:4000`).
3. Create the registration page on Luma (inferred: III next steps say "attach the agent submission form to the Luma event page"; no Luma artifact in Drive) and schedule the Meet from `info@moi.technology` (inferred from who owns the recordings and notes).
4. Create the session's Google Form (Process 2) so submissions can open at the end of the session.
5. Build the deck as a script. S7 deck: 7 slides, each with a bracketed speaker script.
   - `[ DECK · slide N ]` spoken text.
   - `[ >>> SWITCH TO BROWSER: http://localhost:4000 ]` cues.
   - `[ CAREFUL: ... ]` and `[ DON'T say ... ]` guardrails.
   - A typed demo prompt, per-card narration lines, a "LIKELY QUESTIONS" block (Q and A pairs), a close with next-session teaser.
   - The pptx's first text element is "index.html", so the deck was probably authored as HTML and exported (inferred).
6. Record fallback demo clips. `Webinar 7` holds `Vid1.mov` and `Vid2.mov` (modified 2026-08-05 22:11 and 22:33 UTC), created the day before the session (inferred to be backup or promo clips; I did not open them).
7. Rehearse the failure paths. S7's notes contain operational lore that only comes from rehearsal, for example: "If a normal run refuses: an interrupted tamper run left the registry dirty. Rerun it, let it finish."
8. Run the session.
   - Observed order in III: recap of previous sessions, what the session will do, concept, demo 1 (bare SDK, one script, one transaction, verified on Voyage), demo 2 (same thing through an agent framework via a `skill.md`), questions, challenge announcement, roadmap, close.
   - S7 order: identity setup slide, setup/cast, live demo in the browser with cards arriving about 6 seconds apart, a "refusal" demo (tick "Simulate a compromised listing"), a code slide, a "what's missing" slide run with a terminal command first, "where this goes", "go build".
9. Verify the demo live on the Voyage explorer ("Voyage generally sees it before cursor does", III; Cursor is the code editor shown on screen), because the audience can look up every hash.
10. After the call: send attendees a summary with links to the bounty and the GitHub repo; add the submission form to the Luma page; upload step-by-step instructions to the repo (all three are the next steps recorded in the III Gemini notes, assigned to Adithya).
11. Verify submissions on chain by hand ("I'm going to verify each and every agent myself", III).
12. Hand the recording to the editor (Process 3).

### Quality rules and house style

From the S7 deck notes:
- "No code on screen, concepts." Each concept card states the problem, how the file solves it, why it is built that way.
- Run the command first, then talk over the slide (slide 5).
- Say the honest caveat out loud: the demo's forecast is made up, the payment is real.
- Do not overclaim: "DON'T say the env var makes it pay anything".
- Land one clear idea per session ("Models decide preferences. Code decides validity.") and set up the next session.
- Q&A answers prepared for the likely hard questions, including the unflattering ones (seller takes the money and does not deliver: you lose it, session nine fixes that).
- From III: open with callbacks so each session stands on the last.

## Rules and house style

Pulled from Drive evidence only; each line names its source.

- Entity names: MOI, MOI Wallet, Coco (first mention "Coco (also known as Cocolang)"), js-moi-sdk (lowercase), Voyage, Sarva Labs; tagline "The participant layer for AI agents." (Documentation Standard).
- Say participant-centric, not account-centric. The 9 Sep CASA description said "account-centric"; the 14 Sep rewrite fixed it and described the ledger as a graph of tesseracts, not a chain of blocks, with "no per-account chain and no single global chain" (CASA PR 1 revision). The 10 Sep PR 2 appendix still has the old wording.
- Governance wording: the MOI Foundation governs the protocol; Sarva Labs designs and develops, builds the reference implementation and maintains the SDKs, and (flagged TBC) operates the public networks (14 Sep CASA doc).
- Docs: one H1, hand-written 140 to 160 character description, answer-first first paragraph, question-phrased H2s where they answer a question, anchors preserved, stubs `noindex` (Documentation Standard v2).
- Titles: `Page Name | Site Name`, up to 60 characters, no version numbers; no enforced minimum (v2 correction of v1).
- `llms.txt` generated, never hand-edited; verify crawler access with `curl -A "<UA>/1.0" -I <url>` after every Cloudflare or hosting change.
- Builders sessions: concepts on screen, not code; run the command first and then talk; admit what is fake; close with the next session's question; prepare likely-hard-question answers (S7 deck).
- Run-of-show and speaker briefing 48 hours before; notes, recording, resources, actions within 24 hours; Q&A and follow-ups within 48 hours with owners (Adithya's objectives doc).
- Internal review gate before any upstream filing (START HERE).
- Primary-source verification for every claim in a package, with the check named (BG2).
- PR hygiene for upstream repos: GPG-signed commits, conventional prefixes, subject 72 characters or fewer, disclose AI assistance in the PR description where the upstream project asks for it (separate from the in-house rule that commits carry no Claude co-author line or footer), personally review payment and signature logic (BG3).
- YouTube: video AMA clips only (7 Aug standup).
- Weekly slots: Wednesday AMA, Thursday AI/developer session, Friday game night (6 Aug standup).
- Rewards should depend on verified on-chain activity, not completion (Sprint plan).
- Do not state the faucet amount without checking it live (20K versus 100K appear in different Drive docs).

## Glossary

Terms are defined as MOI uses them; "(as used in these notes)" marks my best reading.

- **Builders (MOI Builders):** the live developer webinar series in which Adithya demonstrates one MOI capability end to end and sets a challenge; sessions are numbered with Roman numerals (II, III, IV, VII).
- **S7:** Builders session 7 (Agentic Payments, August 2026); S7 deck is its slide deck with speaker script.
- **Forge (MOI Forge):** the campus cohort programme: kickoff, a two-week hackathon, selection and a 12-week builder programme. **Cohort:** one college's group in that programme. **MOU:** a memorandum of understanding with a college.
- **Launchpad (Agent Launchpad):** the MOI product for creating and registering AI agents; launch video and ambassador onboarding are mentioned here.
- **x402:** a payment scheme built on HTTP status 402; MOI's spec and TypeScript mechanism were packaged for upstream review. **CASA:** the Chain Agnostic Standards Alliance, whose namespaces repo takes a MOI namespace submission (as used in these notes). **CAIP-2:** the chain-agnostic identifier format `namespace:reference`.
- **Gemini notes (Notes by Gemini):** the automatic summary, decisions, next steps and transcript Google Meet's Gemini feature writes for a recorded call; it mis-hears names and numbers.
- **AMA:** ask me anything, a live Q&A on Twitter/X and Telegram. **Game night:** a Friday community event in the marketing calendar.
- **KMOI:** MOI's native asset; **anu** are its atomic units; **fuel** is what an interaction pays to run.
- **MAS0:** an asset standard created without a contract. **MASX:** a logic-backed asset. **MAS1:** the NFT standard.
- **Devnet:** MOI's test network, reset from time to time. **Voyage:** MOI's explorer and dev tooling site. **Faucet:** a service that gives test KMOI to a wallet.
- **Luma:** the event page and registration tool used for webinars and calls.
- **Participant-centric:** MOI treats the participant, not the account, as the unit (not "account-centric"). **Tesseract:** the unit of MOI's ledger, a graph of tesseracts rather than a chain of blocks (as used in these notes). **Network ID:** the identifier of a MOI network (not "chain ID").
- **Coco:** MOI's contract language (also Cocolang). **js-moi-sdk:** the JavaScript SDK. **Hardhat, Foundry:** Ethereum development toolkits, which do not work on MOI. **Soulbound:** an asset that cannot be transferred.
- **KOL:** key opinion leader (influencer outreach). **Galxe, DoraHacks, Superteam Earn, Gitcoin:** third-party platforms for quests, hackathons and bounties. **Moinkee:** a MOI-related NFT programme (as used in these notes).
- **Cursor:** the code editor shown on screen in Builders III.
- **Replay protection:** a check that stops the same signed payment being used twice; in the S7 demo it lives in memory, so restarting the seller resets it. **Seller / buyer:** the two demo agents in the payment demo.
- **SPA:** a single-page app that renders in the browser and shows an empty page to crawlers that do not run JavaScript.
- **Recovery phrase:** the word list that restores a wallet (also called a mnemonic or seed phrase); never read or paste it.
- **GEO / AEO / SEO:** optimising for AI answers, answer engines and classic search. **llms.txt, JSON-LD, noindex, Content-Signal:** see `docs-and-geo.md`.
- **WAF:** a web application firewall; **Cloudflare** is the CDN and host used for the docs sites.
- **GPG-signed commits:** commits cryptographically signed by the author, required by the upstream x402 project.
- **Audit finding tags `[CRITICAL]` to `[INFO]`:** the severity labels in the Points program issues doc.
