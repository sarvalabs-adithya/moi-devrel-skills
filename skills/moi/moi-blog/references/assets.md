## Images inside a post
- Put each file in a folder named for the post under `blog/src/assets/` and reference it relatively, so Astro hashes and optimises it:
  `![A full sentence saying what the picture shows](../../assets/<post>/<file>.png)`
- Alt text is a full sentence that says what the picture shows. A short label is not enough, and the lint warns on an empty one.
- A caption is an italic line under the image, numbered, and it adds a claim: `*Figure 1. The MOI stack. Each rung is forced by the one above it.*` The website's `CONTENT.md` says the brand uses no italic (`moi-devrel/design/references/type.md`, read 2026-10-03), so whether a caption may be italic is open. ASK: Rahul.
- `.prose img` caps the height at 78vh, so a tall diagram is fitted, not stretched.
- Do not copy the figure example in `CONTENT.md`, `DEPLOYMENT.md` or `blog/README.md`. It points at `blog/src/assets/agent-flow.svg`, which exists, is used by no post, and is drawn in the old cream and purple palette with DM Mono type. Copying it puts an off-brand diagram on a Poppins page and the build says nothing.
- Release posts carry no pictures (August decision, commit `902f78e` dropped the August cover).
- A chart can be an SVG you author with the tokens above. `how-ai-agents-pay-each-other-moi` has one: `chart-payment-layer-loc.svg`.
- Never hotlink an image. A remote image is not hashed, cached or checked by the build.
- Files under `blog/public/` are served as they are from the root. Use that only for covers and brand files.

## Covers and og:image
The article page derives the share image from `cover`:
```
const ogImage = cover ? new URL(cover.replace(/\.svg$/, '.png'), Astro.site).href : undefined;
```
1. Put `<name>.svg` and `<name>.png` in `blog/public/covers/`. The PNG must be exactly 1200 by 630, because `Base.astro` hardcodes `og:image:width` and `og:image:height` and sets `twitter:card` to `summary_large_image`.
2. Set `cover: "/covers/<name>.svg"` in the frontmatter.
3. After the deploy run `python3 "$SKILLS/moi-blog/scripts/check-live.py" <slug> --expect-cover`. It also loads the image.
Current state: no post on `main` sets `cover`, and none of the six built article pages contains `og:image` (local build of 2026-10-01; the live September page has none either). `blog/public/covers/` holds an unused pair for the August post. Without a cover, shares show a text-only card. The code says why: a missing card degrades to a text preview, and a wrong one misrepresents the page.
What goes wrong:
- Only the SVG shipped: the build passes, the thumbnail renders, and `og:image` points at a `.png` that returns 404. X, LinkedIn and Slack show a bare text preview. Nothing warns you. The linter reports `cover-png-missing`.
- `cover` set to a `.png`: it works, but the apex listing then uses the PNG as its thumbnail too.
- A cover outside `/covers/`: the listing script resolves it against the blog host and fetches it from the wrong place.
- A cover is optional. The thumbnail on `moi.technology/blog` appears only when `cover` is set, and the blog's own listing never shows one.

## Rasterising an SVG to PNG
`sharp` ships in `blog/node_modules` (version 0.34.5 on 2026-10-02) because Astro's image service pulls it in. It is not at the repo root. Run it from `blog/`:
```
cd blog
node -e "require('sharp')('public/covers/<name>.svg').png().toFile('public/covers/<name>.png')"
```
On 2026-10-02 this rendered the August cover at 1200 by 630, the same size as the committed PNG.
Font caveat, from the previous operator's testing (not re-run on 2026-10-02): sharp's SVG renderer has no web-font loader, so text falls back along the stack to Helvetica Neue unless Poppins is installed on the machine. The shipped August PNG is in the fallback face. For a shape-only asset (a mark, an icon, no `<text>`) sharp is correct. For a cover with text and a Poppins requirement, render in a headless browser, draw to a canvas at 1200 by 630, and export the PNG.
Keep a real fallback stack in cover SVGs: `font-family: Poppins, 'Helvetica Neue', Arial, sans-serif`.

## The logo variant trap
`default-light.svg` is the purple planet with white MOI. `default-dark.svg` is the pale lavender planet. The name says which ground the mark sits on, not what colour it is. The gradient stops prove it:
| File | Gradient stops | Reads on |
|---|---|---|
| `default-light.svg` | `#4b17e5` to `#320f99`, letters `#ffffff` | light and white |
| `default-dark.svg` | `#dbcef9` to `#fff` | dark |
The dark mark shipped first as the newsletter logo (`b8c3dea`) and `85629a5` replaced it with the light one, because the pale mark nearly disappears on white. Two things make it easy to get wrong:
1. The previous operator's older design folder said "Use Default - Dark.svg for light backgrounds", while its own `Default - Dark.svg` carries the pale `#dbcef9` gradient. Trust the gradient stops, not the sentence. The design branch of this library has the corrected rule (`moi-devrel/design/references/logos-and-mascot.md`).
2. Seven of the eight SVG files in the marketing site's `public/brand/logos/SVG/`, and the blog's `default-dark.svg`, have no `<style>` block (checked 2026-10-02). The export lost it, so `.cls-1` and `.cls-2` have no fill and the mark renders black. Only `default-light.svg` (1808 bytes, identical in the blog and in the marketing site's folder) has its `<style>` repaired, and `Base.astro` says so. Copy the mark from `blog/public/brand/logos/SVG/default-light.svg`, or repair the `<style>` by hand. The repaired SVGs in `moi-devrel/design/assets/logos/SVG/` render in colour, and that branch notes that the repaired file in the website's brand folder lists its gradient stops the other way round (`moi-devrel/design/references/logos-and-mascot.md`; ASK: Rahul who owns that folder). The files in `moi-devrel/design/assets/logos/SVG-as-received/` render black: do not use them.
Masthead spec for anything meant to match the blog nav: brand image 30px high, 9px gap, wordmark 16px at weight 700 with `letter-spacing: -0.01em`, "Blog" at weight 400 and 55% ink.

## Images in email
The campaign template is not in this repo. It lives in Mailchimp, and the repo only hosts the images by absolute URL under `https://blog.moi.technology/brand/`.
- Rasterise everything. Gmail strips SVG and Outlook never supported it.
- Serve at twice the display size or more, and set `width` and `height` as HTML attributes as well as styles, because Outlook ignores the CSS.
- Always set `alt`. Many clients block images until the reader allows them.
- No spaces in file names.
- Deploy the image before you paste a template that references it. Until the deploy runs, the URL returns 404.
| Asset | File | Pixels | Displayed |
|---|---|---|---|
| MOI mark | `brand/moi-mark-purple.png` | 160 by 123 | 39 by 30 |
| MOI | `brand/social/moi.png` | 62 by 48 | 31 by 24. Set the height and let the width follow, or the planet is squashed |
| X, LinkedIn, Discord, Telegram, GitHub | `brand/social/<name>-colour.png` | 48 by 48 | 24 by 24 |
The `-colour` set is the current one: X black, LinkedIn `#0A66C2`, Discord `#5865F2`, Telegram `#26A5E4`, GitHub `#181717`, with the MOI mark staying purple and first. The older monochrome files stay in the tree because sent campaigns point at them.

## The cache rule
Never change an image in place under the same file name. Mailchimp caches by URL and offers no purge, in its designer and in the public campaign archive. LinkedIn keeps a broken card against the URL. The 2026-08-24 sequence (`b8c3dea`, `85629a5`, `b150873`) replaced `logo-email.png` twice and the new mark never appeared. A rename to `moi-mark-purple.png` fixed it. Name each image for its variant, so the next change is a new file. Do not delete an old one: past campaigns point at it. Before you share a post on LinkedIn, make sure `og:image` resolves, then run LinkedIn's Post Inspector (the previous operator's advice, not re-checked on 2026-10-02).
