## What a reset does to it
Nothing clears the index. The server fills its MySQL `agents` table from the registry, and on `main` no code deletes a row, so the old registry's agents stay after a wipe (inferred from the code; ASK: Gokul). `/health` answers `ok` through all of it. On 2026-10-02 and 2026-10-03 the index listed 49 agents, 1 verified, and PR #5 was not deployed (its sync endpoint was absent on 2026-10-02).

## Notes
- **E1.** The registry's agent count is not on the Explorer. The previous operator kept an untracked read-only script, `server/check-registry.mjs`, that prints the registry count against the live index (lines `on chain`, `explorer has`, `missing`). It is on that machine only. ASK: Adithya for a copy, or ASK: Gokul for the count. On 2026-10-02 the index showed 49 agents while the registry restored on 2026-09-11 held 144, and 23 of the 49 sat on a host that no longer serves the Launchpad.
- **E2.** On `main` the registry id is the `agentRegistryLogicId` default in `server/src/config.ts`, the September registry `2f3e9469`. The client pins nothing on `main`: the pin in `client/vite.config.ts` exists only on PR #5. The package `js-moi-agent-registry` embeds an old id and reads the environment once when it loads, so a browser registration goes to the embedded one unless the client pins it.
- **E3.** `MOI_MNEMONIC`, a PROD secret, makes the server sign its registry reads as that wallet. On `main` it is required. After a wipe that wallet is gone and every read fails with "account not found". Whether it is set in production, and whose wallet it is, is not known. ASK: Gokul. Option (a): a human registers a wallet in the MOI Wallet app on the new chain, funds it, and the secret's owner replaces the PROD secret, never through chat. Option (b): merge PR #5, whose reader uses a read-only caller (`MOI_READ_CALLER_ADDRESS`, default the account that imported the agents into the registry) when `MOI_MNEMONIC` is empty. A set `MOI_MNEMONIC` never falls back, even when its wallet is gone.
- **E5.** Only variables the workflow names reach the containers. It passes `MOI_MNEMONIC`, `MOI_AGENT_ID`, `MOI_INTELLIGENCE_LOGIC_ID` and `MOI_RPC_URL`, and not `MOI_AGENT_REGISTRY_LOGIC_ID`, `MOI_READ_CALLER_ADDRESS` or `MOI_WS_URL`; a new one needs an edit of the `docker run` block. `MOI_AGENT_ID` and `MOI_INTELLIGENCE_LOGIC_ID` are chain ids a reset wipes (inferred): ask the secret's owner to check them. `MOI_WS_URL` defaults to one hard-coded node address. The client build also takes `VITE_AGENT_REGISTRY_LOGIC_ID`, which no client code reads, so setting it changes nothing.
- **E6.** Merging to `main` runs "Build Push and Deploy Agent Explorer" (about 2 minutes). A manual run with another branch and environment PROD builds that branch as `:latest` and deploys it. The old containers are removed first and there is no automatic rollback. The production containers carry a test name; ASK: Upendhar for the exact names before any log, stop or rollback command.
- **E7.** The sync in full is `moi-launchpad-ops/explorer/references/index-sync.md`. `npm run sync` creates the schema, reads every agent from the registry and seeds participants. The server does not do this at boot. It runs inside the backend container on the VM (inferred). Removing the previous chain's rows, or a leftover test row, is a production-database write: GATE, and decide with Gokul first. PR #5 adds a schedule that reconciles every 4 hours (`SYNC_INTERVAL_HOURS`, default 4); it does not delete rows either.
